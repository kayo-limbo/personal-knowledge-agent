# PostgreSQL 每日聊天配额与费用保护

最后更新：2026-09-08。验收截止：2026-09-13。

## 1. 目标与结果

公开演示站允许注册账号，如果只限制单条输入和输出长度，登录用户仍可不断请求 DeepSeek、消耗余额。这个功能在真正调用模型之前增加两级每日请求配额：

- 每个账号每个 UTC 自然日最多 20 次聊天请求。
- 整个演示站每个 UTC 自然日最多 60 次聊天请求。
- 达到任一上限返回 HTTP 429 和 `Retry-After`，不创建 Conversation/Message，也不调用 DeepSeek。
- 计数放在 PostgreSQL，Render 重启或重新部署后不会清零。
- 两个上限可通过 `CHAT_DAILY_USER_LIMIT` 和 `CHAT_DAILY_GLOBAL_LIMIT` 调整；无效值回退到安全默认值，`0` 不能意外关闭保护。

Neon migration 已执行成功。代码和真实 HTTP 429 已在本地连接 Neon、DeepSeek 验证；当前线上仍运行未包含该功能的 `f3abb8a`，需要统一 push 和重新部署后才能写成公网已生效。

## 3. 数据模型与数据流

`ChatQuota` 不保存聊天正文、邮箱或密钥，只保存：范围、主体 id、UTC 日期、请求数和更新时间。唯一键是 `(scope, subjectId, usageDate)`：用户桶的主体是 Session `userId`，全站桶使用固定主体 `all`。

```text
POST /api/chat
  -> Auth.js 验证 Session
  -> Zod 校验请求体
  -> 确认 DeepSeek 服务端配置存在
  -> PostgreSQL Serializable 事务
       读取当天 user/global 两个桶
       任一达到上限 -> 回滚 -> 429 + Retry-After
       均未达到 -> 两个桶各原子 +1 -> 提交
  -> 创建 Conversation、user/assistant Message
  -> 调用有限 Agent 循环并通过 SSE 输出
```

检查放在会话写入之前，所以被拒绝的请求不会污染历史记录。它放在认证、输入校验和 Key 检查之后，避免匿名请求、非法 JSON 或服务端配置错误消耗配额。

## 4. 关键代码为什么这样写

### 为什么要用户桶和全站桶

只有用户桶时，攻击者可以注册多个账号绕过限制；只有全站桶时，单个账号又可能独占全部额度。两者同时检查，分别控制公平性和整个 DeepSeek 账户的最大请求入口。

### 为什么使用 PostgreSQL，而不是进程内 Map

Render 容器会休眠、重启和重新部署，内存计数会丢失；如果未来恢复 Vercel，多实例之间也不会共享 Map。PostgreSQL 已经是项目必需基础设施，复用它能保持计数持久和跨实例一致，不引入 Redis。

### 为什么需要 Serializable 事务

“先查询是否未满，再递增”若没有隔离，两个并发请求可能同时看到 19，随后都写成 20 以上。Serializable 让数据库检测这种读写冲突；Prisma 返回 `P2034` 时最多重试三次。用户桶和全站桶在同一事务、按固定顺序写入，不能只增加其中一个。

### 为什么失败或取消也计数

一旦配额事务提交，后续请求可能已经向 DeepSeek 发出并产生费用。失败后退还会让客户端通过主动断开反复免费请求，还会引入补偿事务竞态。验收版采用保守计数，简单且安全；输入校验和配置错误发生在计数之前。

### 为什么不用字符数冒充 Token 配额

字符与 token 没有固定比例，Agent 还可能进行多轮模型调用，DeepSeek 服务端搜索内部次数也不是应用可完全控制。当前配额是明确的“进入聊天主链路的请求数”硬门禁；已有输入长度、上下文字符、最大输出、轮数和超时继续作为第二层保护。准确成本统计需要接入供应商 usage 后再做。

## 5. 设计取舍和边界

- UTC 自然日避免 Render、Neon 和本地时区不同产生两个日期桶；对中国用户相当于每天 08:00 重置，错误信息明确写 UTC。
- 全站限额能保护余额，也可能被恶意用户提前耗尽形成拒绝服务。验收前准备固定账号、演示前检查额度，并保留本地录屏；未来可增加管理员预留额度或注册邀请码。
- `ChatQuota.subjectId` 不设 User 外键，因为同表还保存没有 User 的全站桶。用户删除后会留下一条仅含不透明 id 的当日计数，后续可定期删除旧日期桶。
- 数据库或事务异常时返回 503，选择失败关闭，不能因计数服务故障无限制调用模型。
- 环境变量不是秘密，但线上修改后仍要重新部署；默认值 20/60 适合低流量验收，不是通用生产容量建议。

## 6. 面试重点

### 问：为什么唯一索引还不够？

答：唯一索引只能防止同一用户同一天出现两行，不能防止两笔事务同时读到“还剩一次”。还需要 Serializable 隔离或带条件的单条原子 SQL 来保证上限。

### 问：为什么返回 429 而不是普通 SSE error？

答：配额在流开始前就能确定。直接返回标准 HTTP 429，前端现有非 2xx JSON 错误处理可以展示中文原因，`Retry-After` 也让客户端和代理知道何时可重试；没必要先建立一个 200 SSE 再报告失败。

### 问：这是否等于完整计费系统？

答：不是。它是请求入口的硬保护，无法精确反映模型、思考模式、Agent 轮数和上游内部搜索成本。完整系统还要记录每轮 usage、模型价格版本和预算告警。

### 问：为何不引入 Redis？

答：项目是单一验收环境，PostgreSQL 已存在，日配额写入量很低。Redis 会增加部署、免费额度和故障面，当前收益不足。

## 7. 易错点

- 先创建空 assistant 消息再检查配额，导致 429 留下脏历史。
- 只按 IP 限制，经过代理时错误共享一个 IP，或信任可伪造的转发头。
- 只做 `count >= limit` 查询、不在同一事务递增，产生并发越界。
- 将无效环境变量解析成 `NaN` 或 0，从而意外关闭限制。
- 达到用户上限时仍递增全站桶，浪费公共额度。
- 把“每日请求数”描述成“每日 token”或“固定费用”，造成简历和面试表述失真。
- migration 未先部署就发布代码，导致所有聊天因缺表返回 503。
