# 固定知识库检索、上下文注入与引用来源

## 1. 目标与结果

这个功能解决的问题是：聊天虽然已经能调用 DeepSeek，但此前模型只能看到聊天历史，看不到用户在 Knowledge 页面保存的内容。

现在一次聊天请求会先在服务端完成固定检索：

1. 从 NextAuth Session 取得当前用户 `userId`。
2. 从当前问题提取中英文关键词。
3. 只查询该用户自己的 Knowledge 标题、正文和标签。
4. 对候选条目排序，并限制最多 5 条、每条片段最多 1200 字符、片段和元数据合计最多 6000 字符。
5. 把结果作为不可信知识材料加入 DeepSeek 的 system 上下文。
6. 要求模型在使用材料时标注 `[知识库 1]` 这类引用编号。
7. 服务端在回答末尾确定性追加知识库来源，并把“回答 + 来源”一起保存。

因此用户能看到类似结果：

```markdown
项目使用 Docker Compose 组织应用和数据库。[知识库 1]

---

**知识库来源**

- [知识库 1] 暑期考核部署方案
```

这里仍然是“固定 RAG”或“固定知识检索”，不是 Tool Calling Agent。是否检索、何时检索目前由服务端流程决定，不是模型自主决定。

## 2. 相关文件职责

### `src/lib/knowledge-search.ts`

这是不访问数据库的纯逻辑层，负责：

- 中英文关键词提取。
- 构造带 `userId` 的 Prisma 查询条件。
- 候选结果打分与排序。
- 正文片段截取和字符预算控制。
- 知识上下文 Prompt 拼装。
- Markdown 来源列表生成与转义。

把纯逻辑单独放置的原因是它可以不依赖 Next.js、Session 和数据库直接测试。

### `src/lib/services/knowledge-search.service.ts`

这是仅服务端使用的数据库适配层，负责：

- 通过 `server-only` 防止 Client Component 引用。
- 使用 Prisma 查询 `KnowledgeDoc`。
- 把 `userId` 与关键词条件放进同一个 `where`。
- 最多读取 40 个候选条目，再交给纯逻辑层排序。

### `src/app/api/chat/route.ts`

聊天 Route Handler 负责串起完整流程：认证、校验、固定检索、会话写入、上下文注入、DeepSeek SSE、来源追加和回答持久化。

### `src/app/dashboard/chat/components/ChatMessages.tsx`

更新聊天空状态说明，让用户知道聊天已经支持个人知识库检索和引用。

### `tests/knowledge-search.test.ts`

覆盖关键词提取、`userId` 查询条件、排序、空结果、超长内容预算和 Prompt/Markdown 转义。

### `package.json` 与 `tsconfig.json`

新增 `npm test` 命令，并允许无输出的 TypeScript 项目在测试中显式引用 `.ts` 文件。当前测试使用 Node 22 内置的 TypeScript 类型剥离和测试运行器，没有再引入一套测试框架。

## 3. 完整数据流

```text
ChatWorkspace
  -> POST /api/chat
  -> Zod 校验 content / model / thinkingMode
  -> auth() 取得 session.user.id
  -> searchKnowledge(userId, 当前问题)
       -> extractKnowledgeKeywords
       -> Prisma KnowledgeDoc.findMany
            where: { userId, OR: 标题/正文/标签 contains 关键词 }
       -> 内存加权排序
       -> 命中数、单条片段、总字符预算限制
  -> buildKnowledgeContextPrompt
  -> DeepSeek system + 历史消息
  -> SSE 逐段返回模型正文
  -> 服务端追加“知识库来源”Markdown
  -> completeAssistantMessage 一次性持久化完整回答
  -> 浏览器渲染 Markdown
```

最关键的安全边界在数据库查询处：浏览器请求体没有 `userId` 字段，真正用于查询的 id 来自服务端 Session。

## 4. 关键词检索为什么这样写

### 4.1 不直接用整句 `contains`

如果用户问“我的部署方案是什么”，知识正文可能只包含“部署方案”，并不包含完整问句。直接执行：

```ts
content: { contains: "我的部署方案是什么" }
```

很容易漏掉正确条目。

第一版没有引入分词服务。英文按单词切分；连续中文保留较短完整短语，并生成二元词组。例如：

```text
部署方案是什么
  -> 部署方案是什么
  -> 部署、署方、方案、案是、是什、什么
```

常见疑问词会被过滤，关键词总数最多 16 个，避免一个超长问题生成几千个数据库条件。

这种方法不如专业分词、BM25 或向量检索准确，但依赖少、容易解释，适合当前验收版。

### 4.2 为什么数据库只做候选召回

Prisma/SQLite 的 `contains` 适合做简单包含匹配，却不适合表达“标题命中比正文命中更重要”。因此流程分两步：

1. 数据库用标题、正文、标签的 `OR` 找出最多 40 个候选。
2. 服务端内存按字段权重排序。

当前权重为：

```text
标题 8 > 标签 5 > 摘要 3 > 正文 1
```

命中词越长，得分也越高，但长度增益最多计算 8 个字符，防止长句偶然命中后权重无限放大。相同得分时，最近更新的条目优先。

### 4.3 为什么限制候选数和上下文字符

如果把所有知识全文交给模型，会产生三个问题：

- Prompt 过长，响应变慢并增加费用。
- 相关内容被大量无关文本淹没。
- 恶意或错误知识文本影响模型的机会增多。

当前限制是：

```text
数据库候选：最多 40 条
最终命中：最多 5 条
单条片段：最多 1200 字符
片段 + 标题/标签：最多 6000 字符
```

截取正文时会尽量让关键词附近的内容出现在片段中。省略号也计入单条预算；这是单元测试发现并修正过的边界。

字符预算不是精确 token 预算。中文、英文和代码的 token 比例不同，但字符预算实现简单，已经足以给 MVP 做成本保护。

## 5. 上下文注入为什么放在 system 中

聊天历史仍然通过 `messages` 传给 DeepSeek，检索到的知识则追加到 system 内容：

```ts
system: `${SYSTEM_PROMPT}\n\n${knowledgePrompt}`
```

这样可以清楚地区分：

- system：助手规则与本轮检索材料。
- messages：用户和助手的历史对话。

知识材料使用带字段名的 JSON，并放在 `<knowledge_context>` 中。`<`、`>`、`&` 会转成 Unicode 转义，避免知识正文伪造一个真正的 `</knowledge_context>` 提前结束边界。

Prompt 还明确说明知识内容是“不可信数据”，要求模型忽略其中改变角色、泄露提示词或执行操作的指令。

这只能降低 Prompt Injection 风险，不能数学上保证模型永远不受影响。后续还需要检索评估、内容审计和更严格的工具权限边界。

## 6. 引用来源为什么由两部分组成

### 6.1 模型负责行内引用

每个检索结果都有稳定编号：

```text
[知识库 1]
[知识库 2]
```

模型被要求在使用某条知识支持结论时，把编号写在对应句末。这样用户能看出具体句子依赖哪条材料。

### 6.2 服务端负责来源列表

不能完全相信模型每次都会正确生成来源列表。因此服务端根据真实检索结果确定性追加：

```markdown
**知识库来源**

- [知识库 1] 条目标题
```

标题先进行 Markdown 转义，避免一个恶意标题伪装链接或破坏页面结构。

这个列表表示“本次实际检索并注入的来源”。模型是否真的使用某条材料，要看正文中的行内引用。第一版没有做逐句引用正确性验证，这是已知限制。

## 7. 为什么不新增 Message 引用字段

一种方案是修改 Prisma `Message`，增加 JSON 类型的引用元数据，再让前端渲染来源卡片。

当前选择是把来源 Markdown 直接追加到回答正文，原因是：

- 不需要数据库迁移。
- 现有 SSE 和 Markdown 渲染可以直接复用。
- 来源与回答一起保存，刷新和重新登录后不会丢失。
- 当前纵向功能可以独立验收，不同时扩大数据模型范围。

代价是来源暂时不是结构化数据，无法直接实现点击跳转、引用统计和独立样式。等 Agent 循环稳定后，可以给 Message 增加结构化 citation 字段。

## 8. 安全与权限设计

### 8.1 身份认证不等于资源授权

`auth()` 证明用户已经登录，但还需要保证查询只读自己的数据：

```ts
where: {
  userId,
  OR: [
    { title: { contains: keyword } },
    { content: { contains: keyword } },
    { tags: { contains: keyword } },
  ],
}
```

`userId` 与关键词必须在同一个查询中。不能先查询全库再在 JavaScript 中过滤，否则会读取多余的其他用户数据，也容易因异常分支造成越权泄露。

### 8.2 为什么不能接收浏览器传来的 userId

攻击者可以修改请求体。如果 `/api/chat` 接收 `userId` 并直接查询，就可能通过伪造 id 搜索别人的知识库。

当前 `SendChatInput` 只包含会话、问题、模型和思考模式，知识检索身份始终来自 Session。

### 8.3 错误信息为什么分公开与内部

检索失败时，服务端日志记录原始错误，浏览器只收到“知识库检索失败，请稍后再试”。这样既方便开发者排查，也避免把数据库结构或连接信息暴露给用户。

## 9. 空结果与失败行为

### 空结果

没有相关知识时，不会追加伪造来源。system Prompt 会告诉模型可以使用通用知识回答，但必须说明不确定性，并且不能伪造知识库引用。

### 检索失败

检索失败时本次请求返回 HTTP 500，不创建会话和消息，也不调用 DeepSeek。当前功能的目标是确保“知识增强回答”闭环可信，因此第一版没有静默降级为普通聊天。

### DeepSeek 失败

检索成功但模型请求失败时，沿用原聊天逻辑：删除空的 assistant 占位消息，并通过 SSE 返回可理解错误。

## 10. 设计取舍

### 固定检索，而不是立即做 Tool Calling

固定检索路径短、容易测试，可以先证明 Knowledge 数据真的影响回答。代价是每次问题都要搜索数据库，即使问题明显与知识库无关。

下一阶段再让模型通过 `searchKnowledge` Tool Schema 自主决定是否检索，并加入最大轮数、超时和错误处理。

### 关键词检索，而不是向量数据库

关键词检索不需要 embedding 服务、向量数据库和额外费用，适合当前截止日期。代价是同义词和语义相近但字面不同的问题可能召回失败。

### Markdown 来源，而不是结构化引用表

Markdown 能复用现有持久化和渲染。代价是后续要做来源卡片或点击跳转时需要演进数据模型。

## 11. 面试重点

### 问：这已经是 Agent 了吗？

不是。当前是带固定知识检索的 LLM Chat。Agent 至少还需要“模型选择工具 -> 服务端执行 -> 工具结果回填 -> 有限循环 -> 最终回答”。

### 问：如何防止搜索到别人的知识？

用户 id 来自服务端 Session，不来自请求体；Prisma 查询的同一个 `where` 同时包含 `userId` 和关键词条件。

### 问：为什么不用 SQL/Prisma 直接完成排序？

SQLite 的简单 `contains` 适合召回，但当前 Prisma 查询难以清晰表达多字段加权。候选限制为 40 后在内存排序，性能可控且容易解释。数据量增长后应迁移全文检索或专用检索方案。

### 问：引用一定正确吗？

来源列表一定来自真实检索结果，由服务端生成；行内编号是否准确对应结论仍依赖模型。后续可以做引用覆盖率、引用存在性和逐句蕴含评估。

### 问：如何处理知识中的 Prompt Injection？

把知识标记为不可信数据、与系统规则分隔、转义边界字符，并要求忽略其中的操作指令。真正的安全还依赖工具最小权限、参数校验和服务端授权，不能只靠 Prompt。

### 问：为什么按字符而不是 token 限制？

字符预算实现简单、无需额外 tokenizer，适合 MVP。缺点是不精确，后续可以使用与模型匹配的 tokenizer，并统一历史消息与知识片段的总 token 预算。

## 12. 易错点

1. 只在登录处检查身份，却没有在 Knowledge 查询中带 `userId`。
2. 用浏览器请求体里的 `userId` 做授权。
3. 用完整问句执行一次 `contains`，导致大量漏召回。
4. 不限制关键词、候选条数和知识正文长度，造成数据库压力和 Prompt 费用失控。
5. 把知识正文当成可信系统指令，放大 Prompt Injection 风险。
6. 让模型自己生成来源列表，导致标题或编号幻觉。
7. 来源只通过临时 SSE 事件发送，没有持久化，刷新后消失。
8. 截断正文时忘记把前后省略号计入字符预算。
9. 检索失败后仍创建空会话，历史列表出现脏数据。
10. 把固定检索称为 Agent，无法准确解释 Tool Calling 的差异。

## 13. 自动验证

运行：

```powershell

```

1. 中文二元词组和英文小写关键词。

3. 标题命中优先于正文命中。

## 14. 手工验证清单

### 命中与引用

1. 用户 A 新建标题为“暑期考核部署方案”的知识，正文包含独有短语“香港节点 Docker Compose”。
2. 在聊天中提问“我的部署方案是什么？”
3. 确认回答使用知识内容，并在相关句末出现 `[知识库 1]`。
4. 确认回答末尾出现真实知识标题。
5. 刷新页面，确认回答和来源仍然存在。

### 空结果

1. 提问一个知识库完全没有涉及的问题。
2. 确认回答末尾没有虚假的“知识库来源”。
3. 确认模型没有编造 `[知识库 n]`。

### 越权隔离

1. 用户 A 新建包含独有验证码式文本的知识条目。
2. 用户 B 使用相同关键词提问。
3. 确认用户 B 的回答和来源都不包含用户 A 的标题或正文。
4. 切回用户 A，再确认可以正常命中。

### 超长内容

1. 新建一条超过 1200 字符的知识正文，并把关键词放在正文中部。
2. 提问该关键词。
3. 确认能够命中，模型请求没有因整篇全文无限增长。

真实聊天验证会消耗少量 DeepSeek Token；单元测试、lint、TypeScript 和 build 不调用 DeepSeek。

## 15. 后续改进

下一步应保持路线图顺序：

1. 把现有 `searchKnowledge` 复用为 DeepSeek Tool Calling 的服务端执行函数。
2. 定义工具输入 Schema，不能让模型传入 `userId`。
3. 实现 `tool_use -> 服务端执行 -> tool_result -> 再次调用模型`。
4. 加入最大轮数、总超时、单工具超时、取消与错误回填。
5. 持久化工具调用或结构化引用，支持来源卡片和点击打开知识详情。
6. 增加召回率、引用覆盖率和越权隔离的集成测试。
7. 数据量增长后评估 SQLite FTS/PostgreSQL 全文检索，再决定是否需要 embedding 与向量检索。

先完成有限 Tool Calling 循环，项目才应准确称为“个人知识库 Agent”。
