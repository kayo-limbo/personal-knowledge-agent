# 侧边导航等待提示与页面加载骨架

## 目标与结果

页面切换需要服务端鉴权和读取数据库。此前除知识库外缺少 loading 边界，用户在旧页面上等待，容易以为点击无效。本次增加侧栏导航中的转圈提示，以及 Dashboard、聊天、知识库、Prompt、历史、用户管理和系统统计的加载骨架。

这是等待体验优化，不代表数据库查询变快，也不能消除免费实例冷启动。变更需发布后才会影响公网。

## 相关文件职责

- `src/app/components/dashboard/SidebarItem.tsx`：链接后代组件读取 `useLinkStatus`，展示真实导航等待状态；当前页使用 `aria-current`。
- `src/app/components/dashboard/PageLoading.tsx`：复用加载文案和骨架，聊天使用会话侧栏、消息和输入区形状，管理页使用列表形状。
- `src/app/dashboard/**/loading.tsx` 和 Dashboard 根 loading：为各路由提供独立 Suspense 回退，根级回退覆盖其他子页面。

## 数据流

点击 Link → 路由器标记 pending → 侧栏显示转圈 → 目标路由骨架可用时显示骨架 → 服务端完成鉴权与查询 → 真实页面替换骨架。链接 pending 在导航提交后结束，页面数据仍可能继续加载，因此两种反馈需要配合。

## 关键代码解释

`useLinkStatus` 必须放在 Link 后代，放在创建 Link 的组件顶层无法读取该链接状态。状态由 Next.js 管理，不使用点击后定时关闭的假进度；连续点击不同链接时，最后一次导航的 pending 由框架处理。

图标占位始终保持固定宽度，避免出现转圈时菜单文字移动。`role="status"` 提供读屏提示，装饰性骨架使用 `aria-hidden`，减少动态效果偏好的用户不播放旋转或脉冲动画。

`loading.tsx` 由框架建立 Suspense 边界，不需要把服务端查询搬到浏览器。保留默认 Link 预取，不强制预取所有用户数据。骨架需要先到达浏览器，不能保证任何网络条件下零延迟；Dashboard layout 自己的首次鉴权也不由其内部 loading 覆盖。

## 设计取舍与易错点

- 不禁用其他导航，等待时仍可改变目标；不手动 onClick 接管，因此保留键盘和新标签页行为。
- 缓存命中时可能直接显示页面，不应为了展示动画人为增加延迟。
- 骨架是布局近似，不代表真实记录数。
- 不缓存权限或共享用户查询结果来换速度，保持实时角色检查和用户隔离。
- loading 不替代异常处理；请求失败应继续按页面现有错误机制排查。

## 面试重点

能解释真实耗时与感知等待的区别、Link pending 与数据加载的不同生命周期、Suspense 流式回退，以及为什么保留默认预取和鉴权边界。

## 验证方法

1. 使用生产构建启动，登录后逐个点击六个侧栏入口：慢请求应显示对应等待反馈，完成后应被真实内容替换。
2. Chrome Network 开启 Preserve log，使用限速模拟慢网；骨架显示期间切到另一页，确认最终目标正确、没有遗留转圈。
3. 再次访问缓存页面，允许直接显示；测试浏览器前进后退、键盘 Enter 和 Ctrl+点击新标签页。
4. 检查知识库搜索与聊天续聊、滚动布局没有被破坏。
5. 测速关闭人为限速，记录冷访问、连续访问各三次的目标 `_rsc` 请求 Waiting/TTFB、总耗时和内容可见时间。首字节可能只是骨架，不能当作全部数据就绪时间；登录页或健康检查耗时也不能冒充登录后导航耗时。

2026-09-14 验证：TypeScript、定向 ESLint、生产构建通过。本机原 DATABASE_URL 不是 PostgreSQL 协议，第一次构建在收集页面数据时报错；随后仅对子进程设置 PostgreSQL 占位 URL 完成构建，没有更改环境文件或连接实际数据库，因此构建不代表数据库集成测试通过。

当前公网 `/login` 三次只读请求均为 200，TTFB 分别为 16.140、1.052、1.054 秒，总耗时分别为 16.472、1.653、1.234 秒。首次明显较慢，但没有服务端日志证明冷启动原因。这是修改发布前的公开登录页测速，不是已认证侧栏 RSC 请求，也不是优化前后对比。本地 3000 端口未运行服务；尚未进行登录后的真实浏览器回归。

## 后续改进

先按上述方法找出慢请求，再考虑查询并行、请求内去重或部署调整。不要仅根据等待动画消失就宣称性能提升，也不要为本次体验修复扩大基础设施范围。
