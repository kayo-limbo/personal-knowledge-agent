# 登录会话的实时权限

## 目标与结果

管理员修改角色后，对方不必重新登录：下一次服务端请求使用数据库中的最新角色。已删除账号的旧 JWT 不再产生有效 Session。当前已经打开的菜单可能暂时保留旧外观，但服务端不会按旧角色授权；刷新后菜单同步。

## 文件职责与数据流

`src/auth.ts` 验证密码、生成 Session，并在 JWT 回调中按可信 token.id 查询当前用户。`src/lib/validators/auth.ts` 在访问数据库前校验登录输入，避免把 TypeScript 类型断言当成运行时校验。

浏览器 Cookie → Auth.js 验证 JWT → 按 token.id 查询 User.role → Session → 页面、Action、API 各自执行权限判断。Proxy 仍仅做是否登录的快速检查，最终授权由使用完整 auth() 的服务器入口负责。

## 关键代码与设计取舍

原代码只在 `user` 存在时写入角色，之后一直复用 JWT 中的旧值。现在每次回调读取数据库角色。找不到用户返回 null，数据库失败也不回退到旧权限。代价是认证多一次小查询，但单实例验收版优先保证降权及时生效，不增加 Redis 或会话版本基础设施。

登录规则允许已有本地短密码演示账号登录；注册仍要求至少八位密码。不会修改任何已有密码，也不运行 seed。

## 面试重点与易错点

认证证明“你是谁”，授权判断“现在能做什么”。签名有效不表示 JWT 中的权限仍然最新。仅 revalidatePath 只能更新页面缓存，无法撤销旧 Cookie 携带的角色；隐藏菜单也不能代替 Action 权限检查。此方案约束下一次请求，无法撤回已在执行中的请求。

## 验证方法

1. 使用两个临时 ADMIN 登录，保留被操作用户的原 Cookie。
2. 另一位管理员将其降为 USER，用原 Cookie 请求用户管理页并提交角色修改，均应被拒绝或重定向。
3. 将其恢复 ADMIN，原 Cookie 的下一次请求应恢复权限。
4. 删除临时用户后，原 Cookie 请求 Session 不再返回有效用户。
5. 验证登录的空字段、数组字段和超长密码被拒绝；正常登录与退出保持可用。

## 后续改进

若用户量增长，再评估短时缓存和会话撤销版本；必须明确缓存期间降权延迟，不能默认为实时生效。
